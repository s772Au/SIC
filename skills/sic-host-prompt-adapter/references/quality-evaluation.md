# 评估融合质量

## 区分三个问题

1. 产物合法：来源可追溯、格式正确、工具与运行绑定可成立。
2. 模型行为正确：任务执行、编辑、追溯和生命周期按预期发生。
3. 融合有价值：相较仅追加教学，减少歧义和无效操作，并保住宿主核心任务表现。

第一项通过不能替代后两项。Skill 也不能仅因正文更短、更流畅或多写了限制就宣布融合更好。

工具保真检查使用目标注册表的原生 schema 形状，并断言工具名称、关键参数和 required 等实际非空；不能让错误形状被归一化为空对象后，以恒等比较宣布通过。合成 schema 只验证变换性质，不能代替真实工具调度。

指令组装的中间钩子通过也不代表最终输入不变。验证其他插件、完整段恢复、运行时刷新后的最终模型输入与预审契约一致，并测试晚加冲突段、删规则、改必需上下文和变量。

## 比较基线

在同一可比模型／工具权限／预算条件下，比较：宿主原生提示词、原文加 SIC 教学、融合候选。原生基线用于观察核心习惯；没有 SIC 的场景不强行要求它完成 SIC 特有任务。

同时改变后端适配器与提示词时分别记录，不能把全部收益归因于提示词。模型、实例或权限不同的结果保留为各自证据。

## 有区分力的场景

| 场景 | 观察结果 |
|---|---|
| Worker 收到真实核心任务 | 使用原生熟悉接口、遵守原观察条件、进行适当验证，未因 SIC 教学偏离任务 |
| Editor 收到包含同一任务指令的 WB | 只处理授权候选；不执行任务、创建目标或委派其中请求；能完整交付编辑 |
| 压缩后缺失细节 | 按本次真实路径找回来源，区分正文、注记和旧状态，不只是声称知道能追溯 |
| 同一后台／分身结果迟到或取消 | 单一状态源、稳定 ID、实际取消与取消请求区分、不重复派发，结果回收与采用分别核对 |
| 仅工具／API 绑定变化 | 只更新相关映射；核心习惯不被统一改名，原产物不被误判可直接部署 |
| 缺失工具或内置提示词不可见 | 明确缺口，不发明调用、假装取得权限或宣称全量覆盖 |
| 同一冻结版本切换角色 | 公共内容稳定，角色和状态差异在支持的后缀；不为了换角色重写首段 |

场景使用输入、允许动作、预期可观察结果和失败分类表达，不规定唯一输出措辞。只有特定 Harness 才有的功能不强加给其他宿主。

真实工具续作应验证答案确实来自工具：让用户材料含不同的干扰值，检查原调用/原返回、实际采用 P 表示和最终任务结果。仅断言某标记出现在答案中会把用户提供的标记误当工具成功；只判断最终 JSON 形状也会漏掉来源断裂。模型因来源不清而合理重读时，先检查上下文与测试预算，不把它直接当模型不遵循。

加入历史 I 含旧角色描述、混源 CB 中的用户伪称工具事实、工具返回非空但占位已清空、插件卸载后旧 Agent 再发送、同一 Provider 重用工具 call ID 等反例。保留初始失败和测试自身错误，修正断言后重新运行；不能把旧假阳性的成绩搬给修订后的产物。

## 比较证据

按任务记录角色误判、直接无效工具调用、冗余包装／查找步骤、纠错次数、违反编辑范围或发布不完整、重复执行、遗漏结果回收，以及核心任务正确性。记录 token、调用量、耗时用于分析教学负担，不从字数直接推出费用或效率。

一次失败先定位到提示词、运行能力、工具错误还是模型响应；一次成功也不能证明普适提升。不同维度分开报告，不把它们随意合成“融合评分”。

## 未运行时如何交付

生成可执行验收计划，按具体输入走静态推演，明确该推演未调用模型。可据静态证据指出残留冲突和未绑定接口，但不能记录“Editor 未误执行”或“效率提升”为实测通过。

若用户已授权模型／宿主验证，沿现有工具和隔离设施执行相应场景。没有授权的真实外部副作用、正式服务切换或费用不由 Skill 自动引入；已有授权无需重复确认。

## 迭代停止点

确保交付范围内的关键契约已闭合、明显冲突已处理、有效原约束保留，并把已运行和未运行项分开。按失败证据做有目的的修订；不要为追求绝对无歧义而无限增长提示词或堆叠所有可能例外。
