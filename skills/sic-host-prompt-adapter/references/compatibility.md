# Harness 与 SIC 双向兼容

## 本次输入画像

适配前记录下面事实，不以品牌名替代发现：

| 侧面 | 必要信息 |
|---|---|
| Harness 身份 | 名称、可核对版本／构建／摘要、配置或插件影响 |
| 指令面 | 原生指令来源与顺序、可编辑范围、system／developer／其他角色支持、动态上下文入口 |
| 不可见部分 | 缺失的内置提示词或执行政策、可见证据与未验证影响；不宣称覆盖不可见内容 |
| 核心操作 | 实际工具 schema、命名空间／统一执行器／组合调用风格、参数与结果、观察和权限机制 |
| 生态操作 | 目标、后台任务、分身、通知、取消、恢复、预算及最终结果的权威来源 |
| SIC 身份 | 源码版本与运行构建分别记录，能力目录、schema、配置、已验证行为 |
| SIC 协议 | 实际上下文对象、编辑／提交／发布、角色激活、追溯、异步生命周期及冻结规则 |

原生来源可为用户提供的原文、官方或本机实现、配置、受授权运行快照。示例快照只代表该样本。不能读取的内置指令不靠他人转述或常识拼接成“原文”。缺口仍可做局部适配，但交付注明边界。

## 稳定语义与可变绑定

Skill 保留的设计骨架：核心工具熟悉且功能一致、角色清楚、编辑对象／历史边界明确、可追溯、发布语义可靠、重叠工作只有一个权威生命周期。

以下随实现变化：工具名、七种操作的编码方式、对象 schema、角色数量、API 路径、生命周期状态、并发上限、Provider 能力及具体输出格式。发现 SIC 骨架本身演进时也应记录变化及兼容影响，而非假定永不改变。

建立语义到实现的映射，例如：

```text
读取授权原文 → 本 Harness 原生读取入口 → 当前 SIC 存档投影／接口
提交编辑候选 → 本 Harness 交付契约 → 当前 SIC 验证／发布事务
取消后台任务 → 熟悉取消门面 → 当前 SIC 状态＋宿主实际终止证据
```

映射记录 supported、requires_adapter、unknown 或不支持的具体原因。不从版本字符串、操作名字、schema 中一段陈旧 feature_scope 文本单独推断完整能力。

## 兼容判定

- 能力和语义均可核对：生成当前构建可执行产物。
- 核心语义相同、接口变化：只更新对应绑定、示例及必要工具描述，复用其余融合内容。
- 所需能力缺失：输出可审阅方案与明确接线依赖；已授权实现时完成适配器，不以提示词掩盖缺口。
- 未知能力／不可见指令可能影响关键行为：写明局部覆盖和未验证冲突，不擅自弱化宿主限制或虚构支持。
- 实际语义冲突：保留用户的取舍，明确需要修改哪一侧。原生优先不能静默降级成全量改名包装，生态替换也不能退化成双系统并行运行。

不为所有目标规定同一个“最低版本”；按实际所需能力判断。别名或兼容层必须有真实绑定，不能由提示词猜出来。

## 稳定性与迁移

公共教学与稳定工具契约对同一冻结版本保持一致；角色、当前任务、权限范围和可渐进能力走实际受支持的后缀机制。

更新指令措辞、核心 schema 或角色／发布语义可能改变公共前缀，需要新适配版本并按实际新会话／迁移路径激活。不要每轮自动改写公共段；不要在已发布 CB 上原地修补历史。

兼容性记录至少关联原始输入摘要、两端构建、能力映射、生成产物摘要和验证范围。缓存是否实际命中由具体 Provider 证据说明，公共字节一致不替代它。

## 更新范围

Harness 工具增加、SIC API 改名、后台取消增强和角色体系变化分别只影响对应契约。重新检查相关依赖和冲突，不因一个接口改变就全量重写所有核心教学。

DSH 历史参考保留它自己的版本标签。新增目标需要特殊知识时，增加一个局部参考；通用工作流不依赖先查到 DSH 文档，也不要求新目标伪装成 DSH。
