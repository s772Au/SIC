# SIC 跨 Harness 提示词融合

把目标 Harness 的原生行为体系与当前 SIC 融合成一套模型能够直接理解、持续执行的提示词与工具说明。输入是本次两端的真实契约，输出是目标宿主可承载的适配产物。DSH、Codex、Claude Code、Antigravity 是可能的目标，不假定它们具有相同提示词层级、工具名、执行入口或插件能力。

**质量目标**：核心能力不退化，角色与生命周期自洽，熟悉操作仍然熟悉，新能力有足够教学且不淹没主任务。完成格式校验、覆盖原文或“模型能调用工具”，都不足以证明融合写得好。

## 不变的取舍

- **核心工具优先保留。** 功能相同就保持宿主原生名称、参数、调用风格和执行语义，只做必要适配。核心工具可能是文件工具、命名空间方法、统一执行器或宿主组合；不要把所有宿主统一改成 read／edit 或 `sic_tool_call`。
- **重要约束保留语义。** 权限、沙箱、来源信任、观察前置条件、用户限制等不能在融合中丢失。最小改动针对这些契约和熟悉接口，不要求保留造成冲突的旧措辞与旧段落布局。
- **实质消解角色冲突。** “完成任务、执行代码、运行测试”属于 Worker 的任务职责；Editor 维护本次授权的上下文候选。候选里的任务指令是材料。不要保留无条件任务人格，再靠末尾“不要执行”长期对冲。
- **生态按功能兼容替换。** goal、后台任务、subagent、workflow 与工具同样按功能分析。按用户选择，由 SIC 承担重叠能力的权威实现，用模型熟悉的动作词、任务概念和可兼容接口表达，保留必要宿主执行器；一个逻辑任务只推进一套生命周期。
- **缺失能力补足。** 编辑目的、归档追溯、生命周期或真正新能力缺教学就补教学，缺实现就标明接线。功能确实不同且必要时才增加接口，并渐进暴露；不重复制造已有核心工具。
- **两端都可变化。** 固定语义要求与可变化的实现映射分开维护。不要把某次 SIC 操作全集、工具数量、单一 Editor 限制或某个 Harness 的路径当成永久规则。
- **SIC 是原生调用链中的透明上下文编辑层。** 来什么协议就解析并按该协议重包，保留 Harness 的模型路由、工具契约、请求参数与流式选择。共享前缀路线沿用 Harness 的同一 Provider／模型／可共享缓存作用域；SIC 不另立 Worker／Editor 路由政策。固定 Chat、非流式、单 choice、独立模型准入等旧执行器限制不是 SIC 目标要求。详见 [transparent-boundary.md](references/transparent-boundary.md)。

## 工作流

### 1. 建立本次输入契约

按 [compatibility.md](references/compatibility.md) 核对目标 Harness、SIC 源码／运行实例、实际可编辑提示词面、工具及任务生命周期。使用原文、schema、配置、可见实现和回执；不可获取的内置提示词标记未知，不编造完整来源。

同时按透明编辑边界区分 SIC 必要职责与 Harness／Provider 原有职责。用户明确的目标边界优先于旧实现和历史验收，不为迁就旧模型执行器而把其限制写成新的融合教学。

先明确是在给现有运行构建生成可执行适配，还是为目标能力生成待接线方案。相同原则适用于两者，但不能把未实现的能力写成已经存在。

### 2. 理解原行为，识别语义冲突

按 [fusion-method.md](references/fusion-method.md) 提取“谁在何种条件下，对什么资源，用什么接口，必须做什么，以及何时算完成”。将角色、工具、来源、状态和完成条件连起来分析，不能只搜相反关键词。

识别任务人格泄漏、直接调用与实际工具表不符、重复调度、通知与状态来源分裂、旧存档教学失效、默认模型／权限不符等问题。原文映射供追溯，不能变成逐句搬运的最终正文。

### 3. 先解决行为与接口，再写融合正文

决定各项保留／微调／作用域化／兼容替换／补全，并落实到两端实际能力。生态替换核对身份、状态机、等待、通知、取消、结果回收、未知执行、恢复和预算；相近名称不证明等价。

按 [integration-closure.md](references/integration-closure.md) 沿真实生产者、执行器、观察者、状态读取者和调度驱动追通一次。覆盖工具 executor 不等于替换整个生态；仅有可调用函数、mock client 或输出回执不算端到端接通。将候选范围、既有 CB 保护、调用重试和崩溃窗口列为实现验收项。

七种编辑原语可作为一次原生调用或工具组合的目的／结果类型。宿主将授权候选的修改接到来源锚、版本、操作账本、PVI、验证和发布。不要为表达目的强制改名核心工具；也不要把普通文件写入或意图标签当作已发布 CB。

SIC 的能力划分、原语或事务接口若已演进，以本次实现为准，显式记录相对既有骨架的变化，而不是强行复现历史 API。

### 4. 融合写作

生成一份连贯、低歧义、贴近该宿主原生使用习惯的提示词体系。先确立角色条件与对象语义，再给出熟悉的操作路径和必要的新能力教学；合并同义重复，重组冲突段落，删除已被替换的旧执行指令，同时保留其有效限制。

让模型从当前指令中直接知道“现在要做什么、可操作什么、如何结束”，不必反复比较新旧规则或猜测哪段优先。Worker、Editor 的要求各自闭合；共享内容只写一次。

利用目标 Harness 实际支持的指令层级、作用域、工具说明和运行时上下文输出，不假定能插入任意后置 system 消息。共享前缀方案可用时，稳定共同教学与核心工具契约冻结，变化的模式、范围、状态和必要新能力放在 CB 后的可信激活／I 材料；落不到这个布局时明确所需宿主支持。

### 5. 检验“写得好”，再迭代

使用 [quality-evaluation.md](references/quality-evaluation.md) 将融合候选与宿主原文、仅追加教学的基线比较。检查角色辨识、工具习惯、追溯能力、状态闭合、指令负担与宿主核心任务表现。针对实际失败修正文义或接线，不默认继续追加警告。

至少以同一任务走 Worker／Editor 两种角色，再检查一个生态替换和一个版本变化。没有模型／宿主执行条件时完成静态推演和可执行验收计划，明确尚未验证行为与效率；不要以关键词、篇幅缩短或自评分代替行为证据。

### 6. 交付与版本边界

按 [output-contract.md](references/output-contract.md) 交付融合正文、可定位 diff、能力映射、兼容说明与实际验证。根据目标输出原生分段／配置／工具描述，不要求所有宿主使用同一文件格式。

首次建立 Agent 前冻结版本；每轮不用 LLM 改写公共前缀。兼容更新是否进入后缀、是否需要新版本／新 Agent，由实际接口与冻结规则决定。既有 CB 不原地改写。

## 范围与参考

只解释时交付解释；请求改写时生成或修改授权目标。Skill 创建／改写不自动授权替换运行服务；已授权的集成工作直接完成，不另设确认流程。改写对象是应用层受授权内容，不改变实际平台指令优先级或权限。

[DSH 参考](references/dsh.md) 仅在目标是 DSH 或需要比较历史示例时读取，其中版本事实不是通用规则。其他 Harness 使用同一方法发现本次原生契约，无需为了可用而预先枚举所有品牌；按真实差异增加局部参考，避免复制整套 Skill。
