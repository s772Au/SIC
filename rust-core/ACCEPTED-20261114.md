# 接受的三项改动

时间：2026-11-14。针对 HEAD 上一轮的可用性结论，实施建议 1、2，建议 3 本就是
“保持现状”。

## 1. 能力表现在带 payload schema

`GET /api/v2/capabilities` 的每个操作多了 `payload`：

```json
{
  "operation": "source.text",
  "write": false, "model": false,
  "payload": {
    "required": [{"name":"source_id","kind":"string"}, {"name":"unit_id","kind":"string"}],
    "optional": [],
    "notes": "source_id and unit_id are required; read source.read first to get unit IDs."
  }
}
```

字段来源不是手写，而是两条独立路径合并：

1. **实测**：逐个操作发 `{}`，读它报的第一个缺失字段；填上再发，重复到成功或
   因别的原因失败。这套迭代在 95 个操作上跑了一遍。
2. **扫描**：再扫 handler 里的 `required_str` / `field_u64` / `p.get(...)`，
   把只出现在后面路径的字段补上。

两条路径结论冲突的地方逐个人工核对——这正是表里最容易出错的地方，
下面记了实际踩到的几个。

## 2. worker.run 不再只说 “unknown argument”

前：

```
{"error": {"code": "invalid", "message": "unknown Worker run argument"}}
```

后：

```
{"error": {"code": "invalid", "message":
 "worker.run accepts no payload: the Worker reads its own view. Only retry_after_attempt is accepted, and only to resume a persisted attempt. Received: [\"source_id\"]"}}
```

前者听起来像字段名拼错了，调用方会继续试 `context_id`、`job_id`；后者说清了
规则，并回显实际发了什么。

## 3. 三件待议事项：未改动

Signal-Stop 仍只递增 `control_epoch`；`protected_prefix_blocks` 默认 0；
`Advance`/`Adaptive` 仍与 `wait` 行为相同。三个默认值都是关闭或保守，
不选也不会有错误行为。

## 防止表与实现漂移

`tests/capability_schema.rs` 四项检查，任一失败即构建失败：

| 检查 | 防的是什么 |
|---|---|
| 每个操作恰好一条 payload 记录 | 新操作漏登记，宿主看不到字段 |
| 每条记录都有对应操作 | 操作删了但表里留了幽灵行 |
| 字段不能同时是 required 和 optional | 表自相矛盾 |
| notes 提到的 `snake_case` 字段必须在列表里 | 注释许诺了列表没给的字段 |
| 空调用报的字段必须标为 required | 表与 handler 实际校验不符 |

## 实际踩到的错（不是理论风险）

| 现象 | 原因 |
|---|---|
| `chain.checkpoint` 被判为缺少字段 `a` | 错误文本是散文 “a published cut is required”，
  取首词会拿到冠词。测试改为只认 `<field> must be ...` 与单字段 `<field> required` |
| 表里 96 条，只有 79 条能定位到 handler | 27 条 arm 是 `=> self.method(...)` 委托，
  字段在方法体内。这正是要叠加实测数据的原因 |
| `hierarchy.expand` 的 notes 写了 cb_id/wb_id，列表却是空的 | 字符串替换命中了第一个
  相同形态的块而不是目标块。改为按操作名重建整张表 |
| `source.read` 的 `group` 标成 any | handler 实际 `as_bool` |
| `notes` 里的 `payload` 一词被判为进一步字段 | 它是英文词，按 `_` 形状过滤后消失 |

## 验证

```
cargo test --test capability_schema   4 passed
cargo test --test refusal_messages    3 passed
cargo test --workspace               395 passed / 0 failed / 95 binaries
```

真实 release 进程复核：`GET /api/v2/capabilities` 返回 96 个操作，每个都带
`payload`，`source.text` / `memory.page` / `hierarchy.expand` / `worker.run` /
`runtime.discard_unpublished` 五项逐一对照与实测行为一致。
